## 옵티마이저와 인덱스 선택

인덱스 손익분기점

- 인덱스를 통해 데이터를 읽는 비용이 테이블 전체를 직접 읽는 비용보다 높아지는 지점
- 일반적으로 전체 데이터의 약 20~25% 이상을 조회해야하는 쿼리는 테이블 전체를 순차적으로 스캔하는 것이 더 효율적

왜 랜덤 I/O가 더 느릴까?

- 랜덤 I/O → 책의 여러 페이지를 순서 없이 찾아 읽기
- 데이터의 위치를 찾는데 걸리는 시간(탐색시간)이 추가되기 때문

인덱스를 사용하는 효율적인 범위 검색

```jsx
explain select * from items where price between 50000 and 100000;
```

인덱스를 포기하는 비효율적인 범위 검색

```jsx
explain select * from items where price between 1000 and 200000;
```

- type: all

데이터가 많이 부족하다면?

- 풀 테이블 스캑을 선택할 가능성이 있음

## 커버링 인덱스

- 쿼리에 필요한 모든 컬럼을 포함하고 있는 인덱스
- 원본 테이블에 전혀 접근하지 않고 오직 인덱스만 읽어서 쿼리를 처리

커버링 인덱스 적용 전

```jsx
explain 
select item_id, price, item_name 
from items 
where price between 50000 and 100000;
```

- 인덱스에 포함되지 않은 컬럼(item_name)을 조회해야 하므로, 테이블 접근을 피할 수 없음

커버링 인덱스 적용 - 인덱스 컬럼만 조회하는 경우

```jsx
explain 
select item_id, price 
from items 
where where price between 50000 and 100000;
```

- 커버링 인덱스를 활용해 테이블 접근을 피했고(Using index), 인덱스 내에서 where 절의 조건으로 필터링(Using where)을 수행한 매우 효율적인 쿼리

커버링 인덱스 적용 - item_name 추가

```jsx
drop index idx_items_price on items;

create index idx_items_price_name on items ( price, item_name);

explain 
select item_id, price, item_name 
from items 
where price between 50000 and 100000;
```

- idx_items_price_name 인덱스만 읽고 끝나므로, 테이블 접근으로 인한 I/O가 완전히 사라져 훨씬 빠르고 효율적으로 동작

커버링 인덱스의 장단점

장점

- 압도적인 select 성능 향상
- 특히 count 쿼리 최적화

단점

- 저장 공간 증가
- 쓰기 성능 저하
